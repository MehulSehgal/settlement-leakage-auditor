# Settlement Leakage Auditor — Working Prototype

Find the rupees ordinary reconciliation calls "matched" and shouldn't.

This is a runnable implementation of the blueprint: a deterministic
reconciliation engine reconstructs the expected settlement for every
transaction using Razorpay's public formula, compares it to what actually
landed, and escalates only the genuine residuals to a locally-trained
classifier — no LLM, no external API, no network call anywhere in the
pipeline.

## Architecture

```
generate_data.py  ──┐
engine.py           ├─► pipeline_runner.py ──► api.py (FastAPI) ──► SettlementLeakageAuditor.jsx
classifier.py     ──┘         │                    │
                       run_pipeline.py       GET  /api/audit
                       (CLI / file export)   POST /api/audit/run?seed=&inject_break=
                                              GET  /api/audit/case/{payment_id}
                                              GET  /api/audit/exceptions
```

The dashboard is a live client: it fetches from the API on load and re-fetches whenever you
run a fresh batch from the header controls. Nothing in the UI is a static snapshot.

## Run it yourself

**1. Backend — start the API:**

```bash
pip install faker scikit-learn pandas numpy fastapi uvicorn
uvicorn api:app --reload --port 8000
```

This generates the synthetic batch on first startup (seed 42) and runs the full pipeline
immediately, caching the result. Visit `http://127.0.0.1:8000/api/audit` to see the raw JSON,
or `http://127.0.0.1:8000/docs` for interactive API docs (FastAPI's automatic Swagger UI).

**2. Frontend — open the dashboard:**

Open `SettlementLeakageAuditor.jsx` as the Claude artifact, or drop it into any React project.
It expects the API at `http://127.0.0.1:8000` by default; override by setting
`window.SETTLEMENT_AUDITOR_API_BASE` before it mounts if you're running the API elsewhere.

**3. CLI-only (no server), if you just want the numbers:**

```bash
python3 generate_data.py   # synthetic batch of 2,200 transactions, 20 planted leakage cases
python3 run_pipeline.py    # deterministic engine -> classifier -> evaluation -> dashboard_payload.json
```

Everything is seeded, so results are reproducible run to run.

## API endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/health` | Liveness check |
| `GET` | `/api/audit` | Full dashboard payload from the last pipeline run (cached) |
| `POST` | `/api/audit/run?seed=42&inject_break=` | Regenerates a fresh batch and reruns the full pipeline. `inject_break` accepts `duplicate_webhook`, `out_of_order`, or `missing_reference` to demonstrate Phase 4's graceful-degradation story live. |
| `GET` | `/api/audit/exceptions` | Exception queue only |
| `GET` | `/api/audit/case/{payment_id}` | Single case's full evidence chain |

Try the fault injection from the dashboard header, or directly:
```bash
curl -X POST "http://127.0.0.1:8000/api/audit/run?seed=7&inject_break=missing_reference"
```
This deletes one transaction's settlement row after generation and reruns the pipeline — watch
`n_no_settlement_found` in the response go to 1, proving the system queues the gap instead of
crashing or silently mismatching.

## Files

| File | Purpose |
|---|---|
| `generate_data.py` | Synthetic data generator modeled on Razorpay's Payments/Refunds/Disputes/Settlements schema. Plants 20 leakage cases across 5 categories with ground truth recorded separately. |
| `engine.py` | Phase 1 — deterministic engine. Pure arithmetic + rules: expected-settlement formula, ID/amount/date matcher, known-cause rules (duplicate rows, timing-lag). |
| `classifier.py` | Phase 2 — local classifier. RandomForestClassifier trained on engineered features from your own labeled data. Template-based, feature-grounded explanations (never generated text). Hard ₹5,000 auto-resolve ceiling enforced in plain Python. |
| `pipeline_runner.py` | Shared orchestration used by both the CLI and the API — runs the engine + classifier against whatever's in the DB and returns the full payload as a dict. Also owns fault injection for the Phase 4 demo. |
| `run_pipeline.py` | Thin CLI wrapper: runs the pipeline once and writes `dashboard_payload.json` to disk. |
| `api.py` | FastAPI backend. Serves the live pipeline over HTTP with CORS enabled for the dashboard. |
| `settlement_auditor.db` | SQLite file with all 8 tables from the blueprint's data model (payments, refunds, disputes, settlements, expected_settlement, match_results, exceptions, audit_log). Regenerated by `generate_data.py` / `regenerate_data()`. |
| `SettlementLeakageAuditor.jsx` | The dashboard — a single-file React component (also viewable as the Claude artifact) that fetches live from the API and renders the summary, exception queue, case walkthroughs, and evaluation metrics. |

## What the last run found

- **2,200** transactions processed in **~320ms**
- **99.86%** match rate (resolved without human review)
- **₹50,674.45** of planted leakage — **100% recall, 100% precision**, 0 false positives
- **3** cases correctly left in the exception queue — including every case above the ₹5,000
  auto-resolve ceiling, regardless of classifier confidence

Re-run `generate_data.py` with a different `SEED` to get a fresh batch and confirm none of this
is cherry-picked.

## Design choices worth noting to a reviewer

- **Deterministic first.** The engine resolves 2,192 of 2,200 transactions (99.6%) using nothing
  but the formula and simple rules — before the classifier ever runs.
- **The classifier can't invent evidence.** Every explanation string is built from a fixed
  template using the model's actual feature values (a real refund amount, a real days-gap) —
  never free text, so nothing can be hallucinated.
- **The ₹5,000 ceiling is not a suggestion.** It's enforced as a plain `if` statement in
  `classifier.py`, deliberately outside the model, so it's easy to point to on screen.
- **The exception queue is meant to be non-empty.** Two genuinely unexplained cases and one
  ambiguous FX case are left for a human on purpose — an empty queue on a batch this size would
  mean the system is force-matching, not auditing.
